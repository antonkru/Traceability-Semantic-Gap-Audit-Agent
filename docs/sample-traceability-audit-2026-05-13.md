- **Requirements elicited:** 51 atomic requirements (46 FR + 5 NFR) across 11 feature areas.
- **Coverage:** **100%** of functional and non-functional requirements have at least PARTIAL implementation traceability. **~24%** (12 of 51) are COMPLETE (both code and test); **~76%** are PARTIAL (code present, automated test missing or indirect). **0** strict orphans, **0** unmapped hallucinated features after the `578dac4` PR-review hardening.
- **Tests:** 10 xUnit tests in [api/Ripaira.Tests](../api/Ripaira.Tests/) exercise the assessments endpoint, device-id middleware, rate-limit middleware, and `/health`. **The Expo mobile client still has zero first-party tests** — every mobile-side requirement (FR-DEV-1/2, FR-IMG-1..4, FR-UI-1..5, FR-ERR-1..3, FR-CFG-4) is therefore PARTIAL by default.
- **Top semantic risks (POC-priority):**
  1. **FR-RES-1 / FR-RES-4 / FR-RES-5 / FR-AG-2** — response-shape invariants (option↔estimate matching, `confidence ∈ [0,1]`, `low ≤ high`, ≥1 option) are enforced only in prompts; nothing in the orchestrator validates the LLM output before serialisation, so a malformed LLM response becomes a malformed API response.
  2. **FR-SUB-6** — "reject content not decoding as a supported image format with 400" is satisfied by an ImageSharp try/catch, but the request-supplied `mimeType` field is never validated against the actual bytes. A client can send PNG bytes labelled `image/gif` and the request succeeds.
  3. **NFR-LOG-1** — assessment ID and image count are logged at request start; token usage is logged inside each agent **only when `response.Usage` is non-null**, and no end-of-request log line ties token totals back to `AssessmentId`, hampering per-assessment cost grep.
- **Changes since prior audit (`05d331e`):**
  - Dev-only API connectivity screen ([mobile/app/test.tsx](../mobile/app/test.tsx)) is now **triple-gated by `__DEV__`** (nav link, `_layout.tsx` Stack screen, and a `Redirect` inside the route component). This **eliminates the prior "hallucinated feature" finding** for the dev screen.
  - `OpenAI:Model` default in [Program.cs](../api/Ripaira.Api/Program.cs) now matches `appsettings.json` (`gpt-4.1-mini`).
  - `@expo/ngrok` correctly moved to `devDependencies` in [mobile/package.json](../mobile/package.json).
  - The raw-response info log inside `PlanningAgent` is now commented out — slightly tightening cost-of-logs but not changing NFR-LOG-1 traceability.

**Soft orphans (mapped only via prompt or convention; nothing enforces the invariant in code):**

| Req ID | Nature of gap | Remediation |
| --- | --- | --- |
| FR-AG-2 | "One or more solution options" is prompt-instructed only. Nothing rejects an empty `Options` list from the planning agent. | In `AssessmentOrchestrator.AssessAsync`, validate `plan.Options.Count >= 1` after `planning.PlanAsync`; throw to surface 5xx (consistent with FR-AG-7). |
| FR-RES-1 | Option ↔ Estimate matching is prompt-instructed only. The API will pass through a malformed LLM response where some options have no estimate, or estimates reference unknown option IDs. | Add a post-validation in the orchestrator: for every `option.Id`, assert a matching `estimate.OptionId` exists; either fail-closed (5xx per FR-AG-7) or back-fill with an explicit "No estimate produced" placeholder so the contract is self-describing. |
| FR-RES-4 | `confidence` range `[0.0, 1.0]` is prompt-instructed only; type permits any `double`. | Add a clamp or assertion at the deserialization boundary (custom `JsonConverter<double>` constrained to `[0,1]`) or validate in the orchestrator post-LLM. |
| FR-RES-5 | `low ≤ high` invariant unenforced on `CostRange`. | Enforce via compact-constructor validation in the `CostRange` record (or in the orchestrator), so an out-of-order pair from the LLM raises and surfaces as 5xx. |
| FR-RES-6 | `currency` is plain `string`; nothing prevents the LLM from emitting "USD" or "AUS$". | Either constrain to an enum or validate against an allow-list ({"AUD"} for the POC) in the orchestrator. |

> All five soft orphans can be closed by adding a single `ValidateAssessmentResponse(...)` step in `AssessmentOrchestrator.AssessAsync` immediately before composing the `AssessmentResponse` record.

## 6. Semantic Drift

Requirements where the implemented intent diverges from the FRD text:

| Req ID | FRD text | Implementation | Drift | Severity |
| --- | --- | --- | --- | --- |
| **FR-SUB-6** | "The API SHALL reject content that does not decode as a supported image format with 400." | Format validation is performed **only** by attempting to decode the bytes with ImageSharp. The request-supplied `UploadedImage.MimeType` is never read in the API hot path — [ImageProcessingService.cs](../api/Ripaira.Api/Services/ImageProcessingService.cs) always emits `"image/jpeg"` as the output `MimeType`, and the inbound value is discarded. | Outcome matches intent (unsupported bytes → 400), but a client sending PNG bytes with `mimeType: "image/gif"` would succeed. | LOW — outcome correct; either trim `mimeType` from the contract or assert format consistency. |
| **FR-AG-1** | "...invoke a Planning agent with: the job category, the user's description, and all pre-processed images." | [PlanningAgent.cs](../api/Ripaira.Agents/Agents/PlanningAgent.cs) emits `"Category: {category}"` where `{category}` is the raw .NET enum name (PascalCase, e.g. `GeneralHandyman`), not the camelCase wire value (`generalHandyman`). | Cross-layer inconsistency vs FR-SUB-7's camelCase contract. Probably benign for the LLM but documentation-worthy. | LOW |
| **FR-AG-6** | "...clarifying that figures are indicative LLM estimates and that a written quote from a licensed tradesperson is recommended." | The production `Disclaimer` constant satisfies the intent. **But** [StubAssessmentOrchestrator.cs](../api/Ripaira.Agents/StubAssessmentOrchestrator.cs) overrides it with `"STUB RESPONSE — Phase 2 will replace this with real agent output."` Stub lives in the production assembly; only test infra binds it today. | If misconfiguration ever binds the stub in production, the disclaimer text would not satisfy FR-AG-6. | LOW given Phase-3 status; the stub-relocation recommendation in §5 closes this. |
| **NFR-LOG-1** | "The API SHALL log assessment IDs, image counts, and LLM token usage for each request." | `AssessmentId` + image count logged at request start. Token usage logged **inside each agent** only when `response.Usage` is non-null; no end-of-request log line aggregates tokens or correlates them back to the `AssessmentId`. | Cost observability is best-effort and unjoined. | MEDIUM — operationally relevant for cost monitoring once real LLM traffic flows. |

## 7. Risk Ranking (POC-Appropriate Severity)

**Critical (block before any non-POC deployment):**
1. **NFR-SEC-1** — open CORS. *Already acknowledged in inline code comments*; gate via deployment policy.
2. **FR-RES-1 / FR-RES-4 / FR-RES-5 / FR-RES-6 / FR-AG-2** — unvalidated LLM output reaches the wire. A poorly-formed model response becomes a poorly-formed API response, with the mobile UI absorbing the slop.

**Important (POC-acceptable but worth a follow-up):**
3. **NFR-LOG-1** — token usage logging is best-effort and not joined to `AssessmentId`. Affects cost observability.
4. **FR-AG-7** — failure path relies on default ASP.NET 500 with no structured error contract; clients receive whatever ASP.NET emits.
5. **Mobile test coverage** — zero first-party tests. Acceptable for POC, but every mobile-side requirement is currently PARTIAL by default (18 rows in this matrix).
6. **FR-AG-6 stub-bypass risk** — `StubAssessmentOrchestrator` in the production assembly. Currently safe (only tests bind it via `RipairaWebAppFactory`); co-location is the fragility.

**Expected for a POC (no action required now):**
7. Hardcoded `const int DailyLimit = 10` in [RateLimitMiddleware.cs](../api/Ripaira.Api/Middleware/RateLimitMiddleware.cs) is not config-bound. If the number ever changes, the FRD and the constant must move together.
8. In-memory rate-limit counter resets on restart (explicitly documented in FR-RL-4).
9. Hand-synced TypeScript types in [mobile/lib/types.ts](../mobile/lib/types.ts) (explicit `// Replace with OpenAPI codegen later`). Drift risk is bounded by the small contract surface.
10. Expo-template components/hooks left unused under `mobile/components/`, `mobile/hooks/`, `mobile/constants/`.
11. **No SDS document.** The FRD itself defers NFR detail to a future "NFR/architecture doc" that does not yet exist. Documented as a known limitation, not a blocker.

## 8. Recommended Next Steps

1. **Harden the response contract (closes 5 soft orphans).** Add a single `ValidateAssessmentResponse(...)` step in `AssessmentOrchestrator.AssessAsync` after the estimating agent returns. The step should: (a) assert `plan.Options.Count >= 1`; (b) assert that every `option.Id` has a matching `estimate.OptionId` (and vice versa); (c) clamp `confidence` values to `[0,1]`; (d) verify `CostRange.Low <= CostRange.High` everywhere it appears; (e) assert `currency == "AUD"` for the POC. Any failure throws → 5xx, consistent with FR-AG-7.
2. **Add a negative-LLM-shape test** using a stubbed orchestrator (or a fake `IChatClient`) that returns a deliberately malformed result. Confirm the new validation surfaces correctly.
3. **Tighten NFR-LOG-1 observability.** Emit a single end-of-request log line from `AssessmentOrchestrator.AssessAsync` containing `AssessmentId`, total tokens (sum of planning + estimating where available), and elapsed time. This makes per-assessment cost grep-able without joining multiple log lines.
4. **Move `StubAssessmentOrchestrator` out of the production assembly** (into `Ripaira.Tests/` or a new `Ripaira.Agents.Testing` project). Eliminates the FR-AG-6 stub-bypass risk and makes the dependency direction explicit.
5. **Clarify FR-SUB-6 intent.** Either: (a) drop `mimeType` from `UploadedImage` (the API doesn't need it), or (b) assert that the declared `mimeType` matches the bytes ImageSharp detects, and reject mismatches with 400. Pick one and update the FRD accordingly.
6. **Schedule mobile-side testing as a Phase 4 deliverable.** A minimal Jest + React Native Testing Library setup covering [device-id.ts](../mobile/lib/device-id.ts) (UUID persistence), [api.ts](../mobile/lib/api.ts) (header, error path), and the `canSubmit` logic in [index.tsx](../mobile/app/index.tsx) would lift ~18 PARTIAL mappings to COMPLETE.
7. **Author an SDS / architecture document** (or extend §2 of the FRD) covering: the agent pipeline, middleware ordering, the `IChatClient` lifecycle, and the deliberate POC trade-offs. Closes the "no SDS" documentation gap and gives future audits a true three-layer trace.
